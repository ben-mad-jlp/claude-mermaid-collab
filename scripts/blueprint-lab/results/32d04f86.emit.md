## Blueprint: run conductor to LAND a build-green epic (don't wait past its land card)

### Problem
In `src/services/conductor-pass.ts:104-152`, `runConductorPass` bails out with `building-wait` whenever the mission's derived `status` is `'building'` and no criterion action is `discover`/`verify` (`conductor-pass.ts:124-126`). But a build-green epic that has already been rolled up raises an open `epic-ready-to-land` escalation card via `surfaceEpicLand` (`src/services/coordinator-live.ts:1882`, card kind literal at `coordinator-live.ts:1944`) — that card is exactly what the conductor node's own prompt tells it to act on in step 5 (`conductor-pass.ts:75-82`, `escalation_list` → `epic_land_readiness` → `land_epic`). Today the scheduling pass never looks at that card, so the node is never spawned to land it; the pass just says "building" and waits forever, even though the daemon already finished.

### Fix shape — `src/services/conductor-pass.ts`

1. **Import `listOpenEscalations`** alongside the existing `getConductorEnabled` import from `./supervisor-store.js` (import already at `conductor-pass.ts:11`):
   ```ts
   import { getConductorEnabled, listOpenEscalations } from './supervisor-store.js';
   ```
   `listOpenEscalations()` (`supervisor-store.ts:942-947`) returns all open `Escalation` rows project-wide; each row carries `project: string` and `kind: string` (`supervisor-store.ts:107-111`), so filter in-process — there's no project-scoped variant to call instead.

2. **Extend `conductorFingerprint`** (`conductor-pass.ts:49-52`) to take the open-land-card count as a third argument, folded into the returned string so a freshly-surfaced card (count 0→1) changes the fingerprint even when `status`/`actions` are unchanged:
   ```ts
   export function conductorFingerprint(status: string, actions: ConductorActionRow[], landCardCount: number = 0): string {
     const parts = actions.map((a) => `${a.id}:${a.action}`).sort();
     return `${status}|${parts.join(',')}|land:${landCardCount}`;
   }
   ```
   Default parameter keeps this backward-compatible for any other caller (none currently besides `runConductorPass` and the test).

3. **In `runConductorPass`** (`conductor-pass.ts:104-152`), after computing `actions`/`hasGap` (line 123-124), compute the project's open land cards and use them in both the wait-skip and the fingerprint:
   ```ts
   const landCards = listOpenEscalations().filter(
     (e) => e.project === project && e.kind === 'epic-ready-to-land',
   );
   const hasGap = actions.some((a) => a.action === 'discover' || a.action === 'verify');
   // 'building' with no discover/verify gap AND no surfaced land card = the daemon is
   // still working; nothing to direct — wait. An open land card is actionable even
   // while status reads 'building' (a build-green epic that hasn't landed yet).
   if (!hasGap && landCards.length === 0 && status === 'building') {
     return { ran: false, reason: 'building-wait', missionId };
   }

   const fp = conductorFingerprint(status, actions, landCards.length);
   ```
   Do NOT scope `listOpenEscalations()` by mission — the ownership gate in `src/mcp/setup.ts:1971-1990` (`checkOwnership` against the escalation's `todoId`/epic) already refuses a land for any epic outside the conductor's own active mission, so a project-wide card count is safe to use purely as a "there is something to look at" signal; scoping it here would just duplicate logic that already lives at the enforcement point.

No other files need to change: `buildConductorPrompt` already instructs the node to use `escalation_list`/`epic_land_readiness`/`land_epic` (`conductor-pass.ts:75-82`), and `land_epic`'s ownership gate is unchanged.
