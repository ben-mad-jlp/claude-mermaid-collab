I've made the real code changes (not just the blueprint doc — `worktree-manager.ts`, `coordinator-live.ts`, and a new passing test in `worktree-land.test.ts`), and written the corrected blueprint. Here it is verbatim:

Branch GC: `_removeEpicInner` in `src/agent/worktree-manager.ts:2018-2041` currently deletes the
epic accumulation branch with `git branch -D` unconditionally after a land, trusting the caller
that the branch is merged. Fix: re-derive fully-on-master from git before deleting, and skip the
delete + emit a recovery tip when it isn't.

**Change shape** (`src/agent/worktree-manager.ts`):
- New exported `RemoveEpicResult { deleted: boolean; branch: string; aheadCount: number }`,
  placed after `LandResult` (~worktree-manager.ts:158-176).
- `removeEpic`/`_removeEpicInner` return `Promise<RemoveEpicResult>` instead of `Promise<void>`.
- After the worktree remove/prune, call the EXISTING `this.epicAheadOfMaster(epicId, 'master')`
  (worktree-manager.ts:973-984, already does `rev-list --count master..<branch>`) instead of
  adding a new git call. `aheadCount > 0` ⇒ skip `branch -D`, `console.warn` a recovery tip
  (`git log <trunk>..<branch> --oneline`), return `{ deleted: false, branch, aheadCount }`.
  `aheadCount === 0` (fully merged, or branch already gone) ⇒ delete as before, return
  `{ deleted: true, branch, aheadCount: 0 }`.

**Caller** (`src/services/coordinator-live.ts:2300-2310`, the sole production call site): capture
`removeEpic`'s return value; when `!removeResult.deleted && removeResult.aheadCount > 0`, call
`recordFrictionOnce` (same pattern as the existing catch block two lines below) with
`retryReason: 'landed-epic-branch-not-fully-merged'` and a `detail` containing the recovery
git command — this is the "flag" half of the leaf title.

**Acceptance criteria:**
- `RemoveEpicResult` is exported from `src/agent/worktree-manager.ts` and referenced by
  `removeEpic`'s return type.
- `_removeEpicInner` calls `this.epicAheadOfMaster` and branches on its result before any
  `branch -D` call (worktree-manager.ts, inside `_removeEpicInner`).
- `src/services/coordinator-live.ts`'s `removeEpic` call site reads `removeResult.deleted` /
  `removeResult.aheadCount` and calls `recordFrictionOnce` with
  `retryReason: 'landed-epic-branch-not-fully-merged'` on the flagged path.
- New test `src/agent/__tests__/worktree-land.test.ts` — `'removeEpic REFUSES to delete a
  branch with unlanded commits — flags aheadCount, branch survives'` — lands an epic, then
  commits one more change onto the same epic branch, calls `removeEpic`, and asserts
  `deleted === false`, `aheadCount === 1`, and `refs/heads/<branch>` still resolves
  (`git rev-parse --verify --quiet` exits 0).

**Out of scope:** the existing `removeEpicWorktree`/`opts.keepBranch` path (H6a, drop flow) —
unrelated to this GC-after-land path and already leaves the branch alone by design.
Non-production test callers of `removeEpic` (`worktree-concurrency-lock.test.ts`) ignore the
return value already and are unaffected by the signature widening (`void` → object is not a
breaking change for `await`ed, unused-return call sites).
