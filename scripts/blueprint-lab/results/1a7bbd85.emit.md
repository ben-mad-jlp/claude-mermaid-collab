## Blueprint: Teach the UI status vocabulary the `unapproved` mission status

### Root cause
`src/services/mission-store.ts:29-37` defines the backend's `MissionStatus` union with `'unapproved'` as the **first-precedence** value (set when `awaitingApprovalSince` is set — a forged mission not yet human-approved; `mission-store.ts:659`: `if (f.awaitingApproval) return 'unapproved';`). The UI has its own independently-declared `MissionStatus` type at `ui/src/stores/supervisorStore.ts:294-296` that does **not** include `'unapproved'`, and the two exhaustive `Record<MissionStatus, …>` tables that render it — `STATUS_STYLE` and `STATUS_LABEL` in `ui/src/components/supervisor/bridge/rail/missionShared.tsx:38-56`, plus the `statusTooltip` switch at `missionShared.tsx:58-69` — have no entry for it. When the server returns `rollup.status: 'unapproved'`, `StatusPill` (`missionShared.tsx:72-80`) indexes these records with a key that doesn't exist, producing `undefined` classes/label at runtime (a visibly broken pill) despite TS not currently catching the mismatch (the two `MissionStatus` types are structurally different, not shared).

### Changes

**1. `ui/src/stores/supervisorStore.ts:294-296`** — add `'unapproved'` to the UI's `MissionStatus` union, matching the backend's precedence-ordered comment style:

```ts
export type MissionStatus =
  | 'unapproved' | 'abandoned' | 'over-budget' | 'blocked' | 'building'
  | 'needs-verify' | 'needs-discovery' | 'converged';
```

**2. `ui/src/components/supervisor/bridge/rail/missionShared.tsx:38-46`** — add an `unapproved` entry to `STATUS_STYLE`. Use a distinct tone from `blocked`/`over-budget` (both `warning`) — this is not a failure state, it's a gating-on-human state, so reuse the violet family already used for `needs-verify`/`plan` (also a "waiting on an external actor" family) or pick a new neutral-but-attention tone. Simplest citable choice: reuse the violet pill:

```ts
export const STATUS_STYLE: Record<MissionStatus, string> = {
  unapproved:       'bg-violet-100 text-violet-700 dark:bg-violet-900/40 dark:text-violet-300',
  converged:        'bg-success-100 text-success-700 dark:bg-success-900/40 dark:text-success-300',
  ...
```

**3. `ui/src/components/supervisor/bridge/rail/missionShared.tsx:48-56`** — add to `STATUS_LABEL`:

```ts
export const STATUS_LABEL: Record<MissionStatus, string> = {
  unapproved:       'Unapproved',
  ...
```

**4. `ui/src/components/supervisor/bridge/rail/missionShared.tsx:58-69`** — add to the `tooltips` map inside `statusTooltip`:

```ts
unapproved: 'Forged but not yet human-approved — the loop will not drive it until approved.',
```

(Wording lifted from the backend comment at `mission-store.ts:30` for consistency.)

No other file needs a change: `epicDotClass` (`missionShared.tsx:83-89`) operates on epic-status strings, not `MissionStatus`, and is out of scope. `missionView()` (`missionShared.tsx:735-753`) already passes `m.rollup?.status` straight through with no allowlist, so once the type and tables include `'unapproved'` the existing pipeline renders it correctly with no other code change.
