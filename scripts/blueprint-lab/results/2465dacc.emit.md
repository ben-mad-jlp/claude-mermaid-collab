## Blueprint: wire the autonomous LAND path (conductor actor + ownership-gated)

### Ground truth (confirmed by reading the code, not the leaf description)

The server-side machinery described in the leaf **already exists and is correct**:

- `src/services/land-authority.ts` — `LandActor` (`human`/`conductor`/`daemon`), `checkOwnership()` (rules: must be `[EPIC]`, not a bucket epic, must have an owning mission via `findOwningMission()`, mission must be active+non-terminal, and — rule 5, `land-authority.ts:211` — `mission.ownerSession !== actor.session` ⇒ `foreign-mission` blocker), `landAuthority()`, `landedByTrailer()`.
- `src/mcp/setup.ts:1957-2000` — the `land_epic` MCP handler already accepts `{ project, escalationId, allowDirty, actor, session }`, builds the `LandActor`, calls `checkOwnership()` for `actor.kind === 'conductor'`, and refuses with `instruction: 'ESCALATE TO THE HUMAN...'` on a foreign/bucket/unowned epic.
- `src/mcp/setup.ts:1932-1934` — `escalation_list` (→ `supervisorStore.listOpenEscalations()`) is already a registered MCP tool.

**What is NOT wired**: the conductor NODE itself. `src/services/conductor-pass.ts`:

- `CONDUCTOR_ALLOWED_TOOLS` (`conductor-pass.ts:33-40`) does **not** include `mcp__mermaid__escalation_list`, so the node can't even call it.
- `buildConductorPrompt()` (`conductor-pass.ts:56-83`), step 5 (`:75-77`), tells the node to call `epic_land_readiness` then `land_epic` with no mention of `escalation_list`, `escalationId`, `actor:'conductor'`, or `session` — so today's conductor node (if it called `land_epic` at all) would fall through to the **default `actor:{kind:'human'}`** path, silently skipping the ownership gate entirely (the opposite of the intended "ownership-gated" behavior).
- `runConductorPass()` (`conductor-pass.ts:99-145`) never resolves or threads a `session` identifier for the mission it's driving — `MissionSummary.ownerSession` (`mission-store.ts:778`) is read off `listMissions()` rows but discarded at `conductor-pass.ts:104-107` (mapped straight to `getMission()`, whose `MissionRow` has no `ownerSession` field — see `mission-store.ts:45-79`).

This is the actual gap. Existing test `src/services/__tests__/conductor-pass.test.ts:93-99` only asserts the prompt contains `'land_epic'` as a substring — it does not pin the current (incomplete) call shape, so it's safe to extend.

### Change shape

**1. `src/services/conductor-pass.ts`**

- Add `'mcp__mermaid__escalation_list'` to the `CONDUCTOR_ALLOWED_TOOLS` array (`:33-40`).
- Change `buildConductorPrompt(project, missionId, missionTitle)` → `buildConductorPrompt(project, missionId, missionTitle, session)`. Rewrite step 5 (`:75-77`) to:
  1. `mcp__mermaid__escalation_list` and find the open `epic-ready-to-land` escalation(s) whose `todoId` descends from this mission,
  2. confirm with `mcp__mermaid__epic_land_readiness`,
  3. call `mcp__mermaid__land_epic` with `{ escalationId, actor: 'conductor', session: '${session}' }` (interpolate the actual session string into the prompt so the node passes it back verbatim — it has no other way to know its own session id),
  4. if `land_epic` returns `ok:false` with a `foreign-mission`/`bucket-epic`/`no-active-mission` reason, treat that as the "ESCALATE TO THE HUMAN" instruction already embedded in the tool's response and stop (do not retry as human/daemon).
- In `runConductorPass()` (`:99-145`), change the `candidates` derivation (`:104-107`) to carry `ownerSession`/`assigneeSession` alongside the re-fetched `MissionRow`, e.g.:
  ```ts
  const candidates = listMissions(project)
    .filter((m) => m.mission.active)
    .map((m) => {
      const row = getMission(project, m.node.id);
      return row ? { row, ownerSession: m.ownerSession, assigneeSession: m.assigneeSession } : null;
    })
    .filter((c): c is NonNullable<typeof c> => !!c);
  ```
  Update the `target.find(...)` predicate and every subsequent `target.status`/`target.lastConductorKey` read (`:108-122`) to `target.row.status`/`target.row.lastConductorKey`. Derive `const session = target.ownerSession ?? target.assigneeSession ?? 'mission-loop';` (mirrors the existing pattern at `mission-store.ts:593`), and pass it into `buildConductorPrompt(project, missionId, getMissionTitle(project, missionId), session)` at the `invoke()` call site (`:129`).

**2. `src/services/__tests__/conductor-pass.test.ts`**

- Update the `buildConductorPrompt` call at `:94` to pass a 4th `session` arg (e.g. `'s1'`), and extend the assertions at `:93-99` to also check the prompt contains `'escalation_list'`, `'actor'`/`"'conductor'"`, and the literal session string — pinning the new call shape so a future regression is caught.
- Add a coverage case to the `runConductorPass — scheduling` describe block: forge+approve a mission (`forgeApprovedActive()`, which uses `session: 's1'`), run the pass with a spy `invoke` that captures the prompt, and assert the captured prompt contains `'s1'` — proving the mission's `ownerSession` is actually threaded through, not just present in a hardcoded string.
