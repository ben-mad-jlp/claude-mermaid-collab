## Blueprint: Orchestration-node registry for forge/conductor/planner

### Problem

Three top-level "orchestration nodes" (distinct from the per-leaf `LeafNodeKind` nodes registered in `NODE_PROFILE`, `src/services/leaf-executor.ts:710`) each hardcode an identical default-model/default-effort pair in their own file, with near-identical resolution code:

- `src/mcp/tools/mission-forge.ts:251-252` — `FORGE_DEFAULT_MODEL = 'opus'`, `FORGE_DEFAULT_EFFORT: EffortLevel = 'high'`; consumed at `mission-forge.ts:374-375`.
- `src/services/conductor-pass.ts:27-28` — `CONDUCTOR_DEFAULT_MODEL = 'opus'`, `CONDUCTOR_DEFAULT_EFFORT: EffortLevel = 'high'`; consumed at `conductor-pass.ts:136-137`.
- `src/mcp/tools/mission-planner.ts:22-23` — `PLANNER_DEFAULT_MODEL = 'opus'`, `PLANNER_DEFAULT_EFFORT: EffortLevel = 'high'`; consumed at `mission-planner.ts:142-143`.

All three follow the identical two-line pattern:
```ts
const model = input.model ?? resolveNodeModel(project, '<kind>', provider, <KIND>_DEFAULT_MODEL);
const effort: EffortLevel = input.effort ?? listNodeProfileOverrides(project)['<kind>']?.effort ?? <KIND>_DEFAULT_EFFORT;
```
There is already a precedent for a single shared per-kind-defaults table: `NODE_PROFILE` in `leaf-executor.ts:710` for the leaf node kinds (`blueprint`, `implement`, `review`, …). This leaf creates the equivalent table for the three *orchestration*-level kinds and points all three call sites at it, so a future change to "conducting/forging/planning defaults to opus/high" is a one-line edit instead of a three-file hunt.

### Change shape

**1. New file `src/services/orchestration-node-registry.ts`**

```ts
import type { EffortLevel } from '../agent/contracts.js';

/** The daemon's top-level orchestration nodes (forge/conductor/planner) — distinct from
 *  the per-leaf NODE_PROFILE kinds in leaf-executor.ts. Each is high-judgment orchestration,
 *  so all default to opus/high; per-project overrides still flow through
 *  node_profile_override via resolveNodeModel/listNodeProfileOverrides exactly as before. */
export type OrchestrationNodeKind = 'forge' | 'conductor' | 'planner';

export const ORCHESTRATION_NODE_PROFILE: Record<OrchestrationNodeKind, { model: string; effort: EffortLevel }> = {
  forge:     { model: 'opus', effort: 'high' },
  conductor: { model: 'opus', effort: 'high' },
  planner:   { model: 'opus', effort: 'high' },
};
```

**Out of scope:** the per-node `ALLOWED_TOOLS` constants (`FORGE_ALLOWED_TOOLS`, `CONDUCTOR_ALLOWED_TOOLS`, `PLANNER_ALLOWED_TOOLS`) stay where they are — each is a genuinely distinct MCP-tool allowlist, not a duplicated default, and the leaf title/description scope this to defaults. The per-project `node_profile_override` DB table, `resolveNodeModel`, and `listNodeProfileOverrides` (`src/services/orchestrator-config.ts`, `src/services/node-provider.ts`) are unchanged — this only centralizes the *code-level fallback* the DB overrides fall through to.
