## Blueprint: Serve and accept the orchestration kinds on the node-profiles route

**Problem.** `handleOrchestratorRoutes` in `src/routes/orchestrator-routes.ts` still treats the node-profiles matrix as leaf-only:

- `MATRIX_NODE_KINDS` (line 27) is derived solely from `LEAF_NODE_KINDS` (imported from `leaf-executor.ts`), so the GET handler's `rows` (lines 126–146) never contains `forge`/`conductor`/`planner` — even though `LEAF_NODE_GROUPS` (leaf-executor.ts:690-718, already shipped in commit c1f754bb) declares an `'orchestration'` group whose `kinds: ORCHESTRATION_NODE_KINDS` the UI matrix expects rows for.
- `kindRequiresMcp` (orchestrator-routes.ts:35-37) reads `NODE_PROFILE[kind]`, which is `Record<LeafNodeKind, …>` only — calling it with `'forge'|'conductor'|'planner'` reads `undefined.allowedTools` and throws.
- The POST handler (line 172) validates `kind` against `(LEAF_NODE_KINDS as string[]).includes(kind)`, so a POST with `kind: 'forge'|'conductor'|'planner'` is rejected with 400 before ever reaching the MCP guard or the provider/model validation.

The underlying storage (`listNodeProfileOverrides` / `setNodeProfileOverride` / `copyNodeProfilesTo` in `src/services/orchestrator-config.ts`) is already kind-agnostic (`kind: string`), and `src/services/node-provider.ts` already resolves provider/model/effort for orchestration kinds via `resolveOrchestrationEffort` and `resolveNodeProvider`/`resolveNodeModel` fed `ORCHESTRATION_NODE_PROFILE` (used live by `mission-forge.ts`, `mission-planner.ts`, `conductor-pass.ts`). Only the HTTP route is missing the wiring — this is purely additive glue in `orchestrator-routes.ts`.
