## Blueprint: Live two-mission pin measurement against the deployed app

### Context (grounding)

This leaf's own Collab-Todo id (`71b4b916-d897-48b1-bea5-4e7975708d2d`) already has a prior attempt on a dropped branch (commit `a6d70f99`/`ff799223`, "feat: Live two-mission pin measurement against the deployed app") whose only artifact was a hand-written prose report at `docs/conductor-target-live-measurement.md` describing a manual HTTP session against a running `:9002` sidecar. It was never landed. A one-off prose report is not a citable, reproducible deliverable and cannot satisfy a typed diff contract (no real symbol/test to point at), which is almost certainly why it never landed.

The underlying feature this leaf is meant to validate is fully shipped on `HEAD`:

- **Pin storage/read**: `getConductorTargetMission` / `setConductorTargetMission` (`src/services/supervisor-store.ts`).
- **Pin-honoring pass logic**: `runConductorPass` in `src/services/conductor-pass.ts:91-126` — pinned resolution (`:96`), lazy auto-clear on a terminal pin target (`:113-120`, returns `reason: 'target-cleared'`), and the not-yet-actionable hold (`:121-124`, `reason: 'target-not-actionable'`).
- **HTTP surface**: `GET`/`POST /api/supervisor/conductor` in `src/routes/supervisor-routes.ts:896-938` (round-trips `targetMissionId`).

Two existing test suites cover this **separately** but never together:

- `src/services/__tests__/conductor-pass.test.ts:107-190` — unit-level, calls `setConductorTargetMission`/`runConductorPass` directly (never through HTTP) against real forged missions, including the exact two-mission terminal-clear scenario (`test.each(['converged','abandoned'])` at line 164).
- `src/routes/__tests__/conductor-target-route.test.ts` — HTTP-level, round-trips `targetMissionId` through `handleSupervisorRoutes`, but only ever with an arbitrary string id (`'m1'`) — it never calls `runConductorPass`, so it never proves an HTTP-set pin actually drives a real conductor pass or that the route reflects the pass's lazy auto-clear.

That gap — "pin set over the real HTTP route drives the real pass, across two real missions, including the terminal auto-clear and fallback" — is exactly the scenario the dropped prose report measured by hand. This leaf converts that one-off manual measurement into a permanent, automated, citable regression test, bridging both existing suites.

### Change shape

Add **one new test-only file**: `src/services/__tests__/conductor-pass-http-pin.test.ts`.

Mirror the harness setup from `conductor-pass.test.ts:1-30` (stable `MERMAID_SUPERVISOR_DIR` via `mkdtempSync`, per-test project dir, `_resetMissionDbCache`, `forgeMission` via `src/mcp/tools/mission-forge.ts`) plus the `call()` HTTP helper from `conductor-target-route.test.ts:18-26` (build a `Request`, drive it through `handleSupervisorRoutes` from `src/routes/supervisor-routes.ts`).

Two tests:

1. **`'pin set over the real HTTP route drives runConductorPass to that mission, not the other actionable one'`** — forge two real missions (A, B) via `forgeMission`; `addWatchedProject`/`setConductorEnabled`; POST `{project, targetMissionId: A}` through `handleSupervisorRoutes`; call `runConductorPass(project, {invoke: okInvoke})` (imported from `../conductor-pass`) and assert `r.missionId === A` and `r.reason === 'conducted'`, never B.

2. **`'HTTP-pinned mission going terminal auto-clears through a real pass tick, and the route reflects it, then falls back to the other mission'`** — forge A (pin target) and B (fallback, stays actionable); POST-pin A over HTTP; drive A terminal via `setMissionAbandoned` (`../mission-store`); call `runConductorPass` and assert `reason === 'target-cleared'`; GET `/api/supervisor/conductor` over HTTP and assert `targetMissionId === null`; call `runConductorPass` again and assert it now drives B (`r.missionId === B`, `reason === 'conducted'`) — proving the full two-mission live-pin lifecycle end-to-end through the real route and real pass, matching the scenario the dropped doc measured by hand against the live `:9002` server.

No production code changes — the feature is already shipped; this only closes a real, cited coverage gap between two existing suites.

### Acceptance criteria

- `src/services/__tests__/conductor-pass-http-pin.test.ts` exists and contains a test named `'pin set over the real HTTP route drives runConductorPass to that mission, not the other actionable one'` that calls both `handleSupervisorRoutes` (`src/routes/supervisor-routes.ts:909`) and `runConductorPass` (`src/services/conductor-pass.ts:91`) in the same test.
- The same file contains a test named `'HTTP-pinned mission going terminal auto-clears through a real pass tick, and the route reflects it, then falls back to the other mission'` that asserts `reason === 'target-cleared'` from `runConductorPass` followed by a GET through `handleSupervisorRoutes` showing `targetMissionId: null`.
- `bun test src/services/__tests__/conductor-pass-http-pin.test.ts` passes.

### Out of scope

- Re-running the manual, non-reproducible measurement against the actual live `:9002` desktop sidecar — that already happened once (dropped commit `a6d70f99`) and is not durable; this leaf's job is to make the same guarantee permanent as code instead.
- Any change to `conductor-pass.ts`, `supervisor-routes.ts`, or `supervisor-store.ts` — the feature under test is already correct and shipped.
