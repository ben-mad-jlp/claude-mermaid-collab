## Blueprint: align inbox-epic.test.ts with container-close guard + bucket dedup

### Root cause
Two tests in `src/mcp/tools/__tests__/inbox-epic.test.ts` predate two guards that now live in `src/services/todo-store.ts`:

1. **F2 container-close guard** (`todo-store.ts:1523-1528`, throws `ContainerHasOpenChildrenError` defined at `todo-store.ts:369-375`): an explicit `status:'done'` on a container (epic/mission) with open descendants is refused. The test `'a done Inbox is reopened (not duplicated) when a new orphan arrives'` (`inbox-epic.test.ts:89-104`) calls `updateTodo(project, inboxId, { status: 'done' })` at line 93 while the Inbox still has its open child `first` (`first task`, status `planned`) — this now throws instead of succeeding, so the rest of the test (proving `ensureBucket` reopens a done singleton) never runs.

2. **DR-bugfix-bucket-dedupe guard** (`todo-store.ts:1379-1390`, throws `DuplicateBucketError` defined at `todo-store.ts:264-274`): `resolveTodoParent` now refuses to create a second live/done (non-dropped) epic whose normalized title matches an existing bucket. The test `'a live Inbox is returned as-is even when a done Inbox also exists'` (`inbox-epic.test.ts:106-114`) does exactly that at lines 108 and 110 — `createTodo` with title `INBOX_EPIC_TITLE` twice — so the second call now throws `DuplicateBucketError` instead of returning a second row for the "prefer live" assertion to check.

Per the leaf description, product code is correct and unchanged; only the two tests need to be rewritten to assert the new (correct) guard behavior.

### Exact changes — `src/mcp/tools/__tests__/inbox-epic.test.ts`

**Change 1 — test at lines 89-104 (`'a done Inbox is reopened (not duplicated) when a new orphan arrives'`):**
Before marking the Inbox `done` at line 93, settle (drop) its open child `first` so the container-close guard passes:

```ts
test('a done Inbox is reopened (not duplicated) when a new orphan arrives', async () => {
  // Create an orphan to establish the Inbox, then settle its child and mark the Inbox done.
  const first = await addSessionTodo(project, 's1', 'first task', undefined, { inbox: true });
  const inboxId = first.parentId!;
  await updateTodo(project, first.id, { status: 'dropped' }); // settle the open child — F2 container-close guard
  await updateTodo(project, inboxId, { status: 'done' });

  // A new orphan should reopen the done Inbox, not create a second one.
  const second = await addSessionTodo(project, 's1', 'second task', undefined, { inbox: true });
  expect(second.parentId).toBe(inboxId); // same Inbox, not a new one

  const inboxes = listTodos(project, { includeCompleted: true }).filter(
    (t) => t.title === INBOX_EPIC_TITLE,
  );
  expect(inboxes.length).toBe(1); // still exactly one Inbox
  expect(inboxes[0].status).not.toBe('done'); // reopened
});
```
No new imports needed — `updateTodo` is already imported at `inbox-epic.test.ts:9`.

**Change 2 — replace the test at lines 106-114 (`'a live Inbox is returned as-is even when a done Inbox also exists'`):**
Two coexisting Inbox rows can no longer be created. Rewrite the test to assert the create-time guard directly — that a second `createTodo` for the same bucket title is refused once one already exists (regardless of its status):

```ts
test('a second Inbox cannot be created once one already exists — create-time bucket dedupe guard (DR-bugfix-bucket-dedupe)', async () => {
  await createTodo(project, { ownerSession: 's1', kind: 'epic', title: INBOX_EPIC_TITLE, status: 'done' });
  await expect(
    createTodo(project, { ownerSession: 's1', kind: 'epic', title: INBOX_EPIC_TITLE }),
  ).rejects.toThrow(/bucket/i);
});
```
This directly exercises the `DuplicateBucketError` path at `todo-store.ts:1389`. The legacy prefer-live/reopen-adoption behavior stays covered by `bucket-registry.test.ts` and the dedup semantics by whatever bucket-dedupe test already asserts `DuplicateBucketError` (out of scope here — not to be duplicated).

### Out of scope
