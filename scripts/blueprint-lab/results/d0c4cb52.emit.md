**Exact change shape** — new block, copied structurally from the `missions/owner` route (`src/routes/supervisor-routes.ts:296-306`):

```ts
// Approve a forged (unapproved) mission — ratifies its constitution (PROPOSED constraints → active).
if (url.pathname === '/api/supervisor/missions/approve' && req.method === 'POST') {
  try {
    const body = (await req.json()) as Record<string, unknown>;
    const { handleMissionTool } = await import('../mcp/mission-tools.ts');
    const out = await handleMissionTool('approve_mission', body);
    return Response.json(out ? JSON.parse(out) : {});
  } catch (err) {
    return jsonError(err instanceof Error ? err.message : 'Unknown error', 500);
  }
}
```

**Why this shape:**
- `handleMissionTool('approve_mission', args)` (`src/mcp/mission-tools.ts:101-108`) requires `{ project, todoId }` (throws `Missing required: project, todoId` if absent — `src/mcp/mission-tools.ts:103`) and accepts optional `approvedBy`. Passing the raw parsed `body` straight through (same untyped `Record<string, unknown>` pattern as `create_mission`/`delete_mission`/`set_active_mission`/`set_mission_owner` routes) lets `handleMissionTool` itself do the required-field validation and error message — no route-level duplicate validation needed, consistent with sibling routes.
- `handleMissionTool` already returns a JSON string of `{ ...result, rollup, constitutionHealth }` (`src/mcp/mission-tools.ts:107`) and already broadcasts the `session_todos_updated` WS event internally (`src/mcp/mission-tools.ts:106`) — the route does not need to construct a response body or fire a broadcast itself, matching `missions/activate` and `missions/owner`.
- Route path `missions/approve` (not reusing `/api/supervisor/missions` collection path) mirrors the `missions/activate` and `missions/owner` naming convention for single-mission-id action routes.

**Out of scope:** no UI/store wiring (`ui/src/stores/supervisorStore.ts` has no `approveMission` call yet — that's a separate leaf), no changes to `handleMissionTool` or `approveMissionAndConstitution` itself, no new tests file required beyond what's listed below (optional, not blocking).
