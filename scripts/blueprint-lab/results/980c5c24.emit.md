## Blueprint: Per-instance CDP/proxy port and collision-free tab registry keying

### Problem (confirmed by reading the code)

1. **`src/config.ts:165-168`** — `CDP_PORT` is computed once at module load from `process.env.CDP_PORT ?? '9333'` and exported as `export const CDP_PORT`. Every owned-Chrome server (`src/server.ts:83-91`) spawns Chrome with `--remote-debugging-port=${CDP_PORT}` (`src/services/chrome-manager.ts:119`). Two `mermaid-collab` instances on one host (the exact scenario documented in `docs/multi-instance-setup.md:48-79` for `PORT`) both try to bind CDP on `9333` → collision, with no discovery/auto-assign equivalent to `PORT=0` (`docs/multi-instance-setup.md:13,17-21`).
2. Setting `CDP_PORT=0` today doesn't help: `Number('0')` is `0`, not `NaN`, so `config.ts` happily exports `CDP_PORT = 0`, but `ChromeManager.start()` (`src/services/chrome-manager.ts:114-127`) spawns Chrome with `--remote-debugging-port=0` and then `waitForCdp()` (line 129-138) polls `http://127.0.0.1:0/json/version` — which can never succeed. There is no code path that reads back Chrome's actual ephemeral port.
3. `Instance` (`src/services/instance-discovery.ts:10-19`) and `writeInstance(...)` (`src/server.ts:809-819`) publish `port` (HTTP) but never the CDP port, so even a manually-set distinct `CDP_PORT` isn't discoverable via `whereami`.
4. Tab registry: `tabRegistryKey(project, session)` (`src/services/cdp-session.ts:25-31`) and the in-memory `tabRegistry` Map (`cdp-session.ts:34`) are already collision-free — one Map per process, keyed by hashed project root + session. The real collision is `TABS_PERSIST_FILE = '/tmp/.mermaid-collab-tabs.json'` (`cdp-session.ts:79`), a single fixed path on disk. Two concurrently-running server instances both call `persistTabRegistry()` (81-87, last writer wins) and, on startup, `closePersistedTabs(CDP_PORT)` (`server.ts:67-70`) can read another instance's persisted targetIds and `CDP.Close` tabs that belong to a different running instance's Chrome on the same/adjacent port.

### Design

Reuse the exact `PORT=0` → OS-assigned → published-to-discovery pattern already shipped for HTTP (`config.ts:81` `PORT_REQUEST`, `server.ts:695-699,809-819`, `docs/multi-instance-setup.md:13`). Chrome's `--remote-debugging-port=0` already makes Chrome pick a free port and write it as the first line of `<user-data-dir>/DevToolsActivePort` — `ChromeManager` already creates a fresh `userDataDir` per instance (`chrome-manager.ts:117`), so this needs no new isolation, only reading that file back.

### Tasks

**1. `src/services/chrome-manager.ts`**
- Add a private field `private resolvedPort: number | null = null;` and a public getter `get cdpPort(): number { return this.resolvedPort ?? this.opts.cdpPort; }`.
- In `start()` (line 114-127), after `this.proc = this.spawnImpl(bin, args)`, if `this.opts.cdpPort === 0`, poll for `join(this.userDataDir, 'DevToolsActivePort')` to appear (reuse the same poll/timeout pattern as `waitForCdp`), read it, parse the first line as an int, and set `this.resolvedPort`.
- Change `waitForCdp()` (line 129-138) to build `url` from `this.cdpPort` (the getter) instead of `this.opts.cdpPort`, so readiness polling targets the real bound port once resolved.

**2. `src/config.ts`**
- Change `export const CDP_PORT = (() => {...})();` (line 165-168) to `export let CDP_PORT = (() => {...})();` and add `export function setResolvedCdpPort(port: number): void { CDP_PORT = port; }`. Because ES module named imports are live bindings, every existing importer (`src/routes/browser-routes.ts:21,35`, `src/services/cdp-session.ts:13-14` re-export, `src/mcp/tools/browser.ts` call sites) automatically observes the mutation with zero call-site changes.

**3. `src/server.ts`**
- After `await chromeManager.start();` (line 90) and before the `console.log` on line 91, call `setResolvedCdpPort(chromeManager.cdpPort)` (import `setResolvedCdpPort` from `./config.js`), then use the now-current `CDP_PORT` (or `chromeManager.cdpPort`) in the log line so it prints the real bound port instead of the literal `0`.
- Add `cdpPort: chromeManager?.cdpPort` to the `writeInstance({...})` call at `server.ts:809-819` so it's published for discovery (mirrors `port: actualPort` on the same object).

**4. `src/services/instance-discovery.ts`**
- Extend `Instance` (line 10-19) with `cdpPort?: number;` so the new field round-trips through `writeInstance`/`whereami` without breaking existing consumers of the interface.

**5. `src/services/cdp-session.ts`**
- Replace the hardcoded `const TABS_PERSIST_FILE = '/tmp/.mermaid-collab-tabs.json';` (line 79) with a per-instance path: import `deriveSessionId` from `./instance-discovery.js` and `MERMAID_SESSION` from `../config.js` (both already used/importable in this file's neighborhood — `MERMAID_PROJECT` is already imported at line 17), and `tmpdir` from `node:os`, then compute `const TABS_PERSIST_FILE = join(tmpdir(), \`.mermaid-collab-tabs-${deriveSessionId(MERMAID_PROJECT, MERMAID_SESSION)}.json\`);`. This makes the persisted-tabs file collision-free across concurrent instances, matching the same `(project, session)` → `sessionId` scheme already used for the HTTP discovery file (`instance-discovery.ts:89-91`).

**6. `docs/multi-instance-setup.md`**
- Add a short subsection under "Background: The Port Collision Problem" (after line 13) documenting `CDP_PORT=0` auto-assignment and the new `cdpPort` field in `Instance` records, mirroring the existing `PORT=0` explanation.

**7. New test file `src/services/__tests__/chrome-manager.test.ts`**
- Using injected `spawnImpl`/`fetchImpl` (both already injectable per `ChromeManagerOpts` at `chrome-manager.ts:75-86`) and a temp `DevToolsActivePort` file written by the test fake, assert that `new ChromeManager({cdpPort: 0, spawnImpl, fetchImpl}).start()` resolves and `.cdpPort` returns the port parsed from the fake file (not `0`).

### Out of scope
- Changing `tabRegistryKey`'s format (already collision-free in-process; test `src/services/__tests__/cdp-session.registry-key.test.ts` already covers it).
- Threading a proxy/CDP port through every MCP tool call site — the live-binding `export let CDP_PORT` makes that unnecessary.
- `electron-view` / externally-owned-Chrome mode, where a human/Electron already supplies an explicit `CDP_PORT`.
